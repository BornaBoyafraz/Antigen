# Contributing

Thank you for helping improve Antigen. Keep changes focused, include tests for
new logic, and describe any effect on measured behavior or documented limits.

## Development setup

Antigen supports Python 3.10 and 3.12 in continuous integration. From the
repository root:

```bash
python3 -m venv .venv
.venv/bin/pip install --upgrade pip
.venv/bin/pip install -e ".[dev]"
```

The project runs locally without API keys or external services.

## Required checks

Run all three checks before opening a pull request:

```bash
.venv/bin/ruff check .
.venv/bin/mypy .
.venv/bin/pytest -q
```

Ruff checks imports and likely defects, mypy checks project-owned Python code,
and pytest exercises the classifier, explanations, evaluation harness, API,
conversation scoring, benchmark, and packaging.

To print the same branch-coverage report used in continuous integration:

```bash
.venv/bin/pytest -q --cov=. --cov-report=term-missing
```

Coverage is informational and has no minimum threshold.

To exercise the application manually:

```bash
.venv/bin/python examples/demo.py
.venv/bin/uvicorn api.app:app --reload
```

The second command serves the API and browser demo at
`http://127.0.0.1:8000`.

## Regenerating the dataset

`data/generate_dataset.py` is the source of the synthetic labeled corpus.
Update its seed examples or template banks rather than editing generated rows
in `data/prompts.jsonl` by hand, then regenerate from a fresh process:

```bash
.venv/bin/python data/generate_dataset.py
```

The script uses a fixed random seed, prints counts by label and category, and
rewrites `data/prompts.jsonl`. Review the generated diff, confirm the counts are
expected, and run the full required checks. If the corpus changes, update
dataset-size or evaluation claims in the README, model card, and architecture
documentation with fresh measured values.

The separately authored adversarial suite is generated by
`eval/build_adversarial_suite.py`:

```bash
.venv/bin/python eval/build_adversarial_suite.py
```

Keep it independent from the training-data generator so it remains a useful
check on unseen phrasing.

## Code style

- Support Python 3.10; provide a fallback for standard-library features added
  in later Python versions.
- Start Python modules with a descriptive module docstring followed by
  `from __future__ import annotations`.
- Add type hints to functions and keep the ruff line-length setting of 100
  characters in mind.
- Add focused tests for new behavior and regression tests for bug fixes.
- Keep model-performance and security claims tied to reproducible measurements,
  and state important limitations plainly.
- Avoid unrelated refactors in feature or fix changes.

When adding a top-level runtime module, also add it to `py-modules` in
`pyproject.toml`, the relevant `COPY` instruction in `Dockerfile`, and
`RUNTIME_MODULES` in `tests/test_packaging.py`.

## Pull requests

Explain the problem, the chosen approach, and how the change was verified.
Include screenshots for visible web-demo changes and updated evaluation output
when a change affects model behavior. Do not commit virtual environments,
caches, generated model binaries, or local editor files.
